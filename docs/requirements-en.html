1. Project Goals

This project delivers a simulation skeleton library independent of any specific domain, simcore. It is responsible for managing "which entities exist", "how time advances", and "how to access entities by type", but it does not prescribe the specific content of the simulation. Any course project that needs discrete-time-step simulation should be able to introduce simcore through add_subdirectory and run by writing only its own entity types.

Core design constraints (throughout this document):

  • simcore is a library, not an application. There is no "single main program" in the repository.
  • Adding an entity type is only allowed to modify the user's own files; no source code of simcore may be modified.
  • The public API must be stable, documented, and tested; the internal implementation may be adjusted freely.

3. Functional Requirements

3.1 Core Components (must implement)

FR-1 Time Step Driver Stepper

The following public interface must be provided (signatures may be fine-tuned; semantics must not change):

namespace simcore {
class Stepper {
public:
    explicit Stepper(Registry& reg);

    // Advance with a fixed step; when duration is not an integer multiple of step, the final frame uses the remainder
    void run(double duration, double fixed_step);

    // Advance a single time step
    void step(double dt);

    // Current accumulated simulation time
    [[nodiscard]] double elapsed() const noexcept;
};
}

Requirements:

  • Call each entity's update(dt) in registration order (or a user-specified priority).
  • Multi-threading is not supported; if extended later, the single-threaded semantics must remain unchanged.

FR-2 Entity Container and Lifetime Registry

namespace simcore {
class Registry {
public:
    // Construct and register an entity of type T, returning a type-safe handle
    template <class T, class... Args>
    EntityHandle<T> spawn(Args&&... args);

    // Request destruction; actual destruction is deferred until the current update loop ends and is then executed uniformly
    template <class T>
    void despawn(EntityHandle<T> h);

    // Iterate by type
    template <class T>
    View<T> view();

    std::size_t entity_count() const noexcept;
};
}

Requirements:

  • Use type erasure (std::unique_ptr<EntityBase> or an equivalent approach) to store heterogeneous entities.
  • despawn must be deferred, ensuring that destroying an entity during a view<T>() traversal does not invalidate iterators or cause a crash. This behavior must be covered by unit tests.
  • The template parameter T of spawn must satisfy that update(dt) is callable (constrained with a C++20 concept; see FR-4).

FR-3 Type-Safe View View<T>

template <class T>
class View {
public:
    // Supports range-based for; during iteration, only entities of type T are produced
    Iterator begin();
    Iterator end();
};

Requirement: View<T> traversal complexity is not required to be O(1) for locating, but the complexity of a single full traversal must not exceed O(N) (N is the total number of entities).

FR-4 Entity Concept Constraint

template <class T>
concept Entity = requires(T t, double dt) {
    { t.update(dt) } -> std::same_as<void>;
};

Requirement: a type that does not satisfy Entity must produce a readable compile-time error at spawn, rather than a deep template error. An example of the error message must be given in the documentation.

FR-5 Aggregate Header

include/simcore/simcore.h must expose all public APIs in one place, so that users only need #include <simcore/simcore.h>.

3.2 Example Program (must implement)

examples/particle_demo.cpp:

  • No more than 200 lines (including comments).
  • Define at least 2 different entity types (such as Particle, BoundedBox) to prove that heterogeneous entities coexist.
  • Demonstrate the four core APIs spawn / despawn / view / run.
  • Built through the CMake target simcore_demo, with no third-party dependency other than simcore.
  • After running, print a readable simulation summary to standard output (total time, changes in entity count, etc.).

3.3 Unit Tests (must implement)

At least the following cases must be covered under tests/, and all must be executed through ctest:

IDCaseAssertion points
T1Fixed-step advancementTotal duration matches elapsed(), error ≤ 1e-9
T2Multiple entity types coexistentity_count() is correct; the update of both types is called
T3Destruction during traversalCalling despawn inside view<T>() does not crash; the entity count is correct after the loop ends
T4Handle invalidationThe behavior of calling despawn on an already destroyed handle is defined (idempotent or assertion; choose one and document it)
T5Concept constraintspawn of an illegal entity type fails to compile (may use static_assert or a compile-failure test)

There is no hard threshold for coverage, but T1–T3 are mandatory; missing any of them means the FR is incomplete.

3.4 Optional Enhancements (do not affect acceptance; do them only with spare time)

  • Type-safe event bus: publish<T>() / subscribe<T>().
  • Stepper supports priority ordering.
  • A simple performance benchmark (bench/) comparing per-step time with N=10⁵ entities.

5. Documentation Requirements

5.1 Doxygen (mandatory)

  • All public declarations must have @brief; interfaces with parameters/template parameters must have @param / @tparam.
  • Each public component must have at least one @code example.
  • Provide docs/Doxyfile; CMake provides the doc target, and running cmake --build build --target doc generates HTML.
  • The generated result is not required to be committed, but the generated page must be opened live during the demonstration.

5.2 Handwritten Guide docs/guide.md (mandatory)

Target reader: another course project group. The content must include:

  1. A one-sentence explanation of what simcore is and what it does not do;
  2. A five-minute quick start: the complete code from add_subdirectory to writing the first entity and running it;
  3. The steps to add a new entity type (emphasizing "touch only your own files");
  4. The meaning and resolution of common compile errors (covering at least the concept constraint failure in FR-4).

5.3 README (mandatory)

Must include: a one-paragraph project positioning, three lines of build commands, links to docs/guide.md and Doxygen, the license, and a description of the directory structure. Optional: a build status badge.

6. Git Collaboration Standards

6.1 Branches and Merging

  • main is a protected branch; direct pushes are prohibited.
  • Each person branches feature/<name-pinyin>-<feature> from main and merges through a Pull Request when finished.
  • Each PR requires at least 1 other member's Approve before merging (a formal review is sufficient, but a comment must be left).
  • push --force to main is prohibited.

6.2 Commit Messages

Format: <type>: <short description>, type ∈ {feat, fix, docs, test, build, refactor, chore}.

  • Semantically empty messages such as update, fix bug, and . are prohibited.
  • Pushes of unfinished code must be prefixed with WIP: and squashed into clean commits before merging.
  • Each member's commits must be distributed throughout the entire development cycle; concentrated commits in the final week are prohibited (this is a directly observed point of the teamwork score).

7. Demonstration Requirements

The duration is per course regulations (assumed 10–15 minutes). Divide the work along the following narrative line, not by mechanically splitting the time:

7.1 Member A — Positioning and Reusability Argument (about 3 minutes)

  • Explain "why build a library instead of an application";
  • Show the abstraction boundary diagram (one slide is enough);
  • Open the Doxygen-generated documentation page to prove that the documentation is generated from source comments and stays in sync with the code.

7.2 Member B — Live Functionality Demonstration (about 5 minutes, key part)

  1. Build and run simcore_demo, and explain the meaning of the output;
  2. Create a new file live, write a minimal entity (3–5 lines), modify the demo's main to introduce the entity, then recompile and run successfully.
  3. State clearly: "Adding an entity modified only user files; simcore source code has zero changes."
Step 2 is mandatory. If the live compilation fails, both functional and innovative may be judged incomplete. Rehearse at least 3 times in advance and prepare an offline build environment (not dependent on live network access).

7.3 Member C — Engineering and Collaboration (about 3 minutes)

  • Open the repository's Insights / Network page to show the merge history of each member's branches;
  • Point out one specific PR and explain the review and merge process;
  • Explain how the tests are run (ctest).

10. Out-of-Scope Items (explicitly not done)

The following content is outside the scope of this project; proposers must explain its specific contribution to the rubric, otherwise it will not be included:

  • Graphical user interfaces, visual rendering, OpenGL / SDL integration;
  • Network communication, multi-threaded scheduling, parallel simulation;
  • Serialization / save systems;
  • Plugin systems, scripting bindings (Lua / Python);
  • Example programs exceeding 200 lines.
Reason: under the rubric, this project's scoring points are concentrated in reusability, documentation quality, and collaboration traces, not the number of features. Scope creep would squeeze the documentation and rehearsal time in W6–W7, and the marginal benefit would be negative.
