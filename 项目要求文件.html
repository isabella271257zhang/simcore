1. 项目目标

本项目交付一个与具体领域无关的仿真骨架库 simcore。它负责管理「有哪些实体」「时间如何推进」「如何按类型取用实体」，但不规定仿真的具体内容。任何需要离散时间步仿真的课程项目，都应能通过 add_subdirectory 引入 simcore，只编写自己的实体类型即可运行。

核心设计约束（贯穿全文）：

  • simcore 是库，不是应用。仓库中不存在「唯一的 main 程序」。
  • 新增一种实体类型，只允许修改使用者自己的文件，不得修改 simcore 的任何源码。
  • 公共 API 必须稳定、有文档、有测试；内部实现可自由调整。

3. 功能需求

3.1 核心组件（必须实现）

FR-1 时间步驱动器 Stepper

必须提供以下公共接口（签名可微调，语义不可变）：

namespace simcore {
class Stepper {
public:
    explicit Stepper(Registry& reg);

    // 以固定步长推进；duration 不是 step 的整数倍时，最后一帧使用余量
    void run(double duration, double fixed_step);

    // 推进单个时间步
    void step(double dt);

    // 当前累计仿真时间
    [[nodiscard]] double elapsed() const noexcept;
};
}

要求：

  • 按注册顺序（或用户指定的优先级）依次调用各实体的 update(dt)。
  • 不支持多线程；若后续扩展，须保持单线程语义不变。

FR-2 实体容器与生命周期 Registry

namespace simcore {
class Registry {
public:
    // 构造并注册一个 T 类型实体，返回类型安全的句柄
    template <class T, class... Args>
    EntityHandle<T> spawn(Args&&... args);

    // 请求销毁；实际销毁延迟到当前 update 循环结束后统一执行
    template <class T>
    void despawn(EntityHandle<T> h);

    // 按类型遍历
    template <class T>
    View<T> view();

    std::size_t entity_count() const noexcept;
};
}

要求：

  • 使用类型擦除（std::unique_ptr<EntityBase> 或等价方案）存储异构实体。
  • despawn 必须延迟执行，保证在 view<T>() 遍历过程中销毁实体不导致迭代器失效或崩溃。此行为必须有单元测试覆盖。
  • spawn 的模板参数 T 必须满足 update(dt) 可调用（用 C++20 concept 约束，见 FR-4）。

FR-3 类型安全视图 View<T>

template <class T>
class View {
public:
    // 支持 range-based for；迭代期间只产出 T 类型实体
    Iterator begin();
    Iterator end();
};

要求：View<T> 遍历复杂度不要求 O(1) 定位，但单次完整遍历的复杂度不得高于 O(N)（N 为实体总数）。

FR-4 实体概念约束

template <class T>
concept Entity = requires(T t, double dt) {
    { t.update(dt) } -> std::same_as<void>;
};

要求：不满足 Entity 的类型在 spawn 时产生可读的编译期错误，而非深层模板报错。此点需在文档中给出错误信息示例。

FR-5 聚合头文件

include/simcore/simcore.h 必须一次性暴露所有公共 API，使用者只需 #include <simcore/simcore.h>。

3.2 示例程序（必须实现）

examples/particle_demo.cpp：

  • 不超过 200 行（含注释）。
  • 定义至少 2 种不同实体类型（如 Particle、BoundedBox），证明异构实体共存。
  • 演示 spawn / despawn / view / run 四个核心 API。
  • 通过 CMake target simcore_demo 构建，不依赖除 simcore 外的任何第三方库。
  • 运行后在标准输出打印可读的仿真摘要（总时间、实体数变化等）。

3.3 单元测试（必须实现）

tests/ 下至少覆盖以下用例，全部通过 ctest 执行：

编号用例断言要点
T1固定步长推进总时长与 elapsed() 一致，误差 ≤ 1e-9
T2多类型实体共存entity_count() 正确；两种类型的 update 均被调用
T3遍历中销毁view<T>() 内调用 despawn 不崩溃，循环结束后实体数正确
T4句柄失效对已销毁句柄调用 despawn 的行为已定义（幂等或断言，二选一并文档化）
T5概念约束非法实体类型的 spawn 无法编译（可用 static_assert 或编译失败测试）

覆盖率不设硬性门槛，但 T1–T3 为强制项，缺失即视为 FR 未完成。

3.4 可选增强（不影响验收，时间富余再做）

  • 类型安全事件总线：publish<T>() / subscribe<T>()。
  • Stepper 支持优先级排序。
  • 简单的性能基准（bench/），对比 N=10⁵ 实体下的单步耗时。

5. 文档要求

5.1 Doxygen（强制）

  • 所有 public 声明必须有 @brief；带参数/模板参数的接口必须有 @param / @tparam。
  • 每个公共组件至少有一个 @code 示例。
  • 提供 docs/Doxyfile；CMake 提供 doc target，执行 cmake --build build --target doc 生成 HTML。
  • 生成结果不强制入库，但演示时须现场打开生成页面。

5.2 手写指南 docs/guide.md（强制）

读者定位：另一个课程项目的小组。内容必须包含：

  1. 一句话说明 simcore 是什么、不做什么；
  2. 5 分钟上手：从 add_subdirectory 到写出第一个实体并运行的完整代码；
  3. 新增实体类型的步骤（强调「只碰你自己的文件」）；
  4. 常见编译错误的含义与解决方式（至少覆盖 FR-4 的概念约束失败）。

5.3 README（强制）

必须包含：项目定位一段话、构建命令三行、指向 docs/guide.md 与 Doxygen 的链接、许可证、目录结构说明。可选：构建状态徽章。

6. Git 协作规范

6.1 分支与合并

  • main 为保护分支，禁止直接推送。
  • 每人从 main 切出 feature/<姓名拼音>-<功能>，完成后以 Pull Request 合并。
  • 每个 PR 至少 1 名其他成员 Approve 后方可合并（形式审查即可，但须留下评论）。
  • 禁止 push --force 到 main。

6.2 提交信息

格式：<type>: <简短描述>，type ∈ {feat, fix, docs, test, build, refactor, chore}。

  • 禁止 update、fix bug、. 等无语义信息。
  • 未完成代码推送须加 WIP: 前缀，合并前 squash 为干净提交。
  • 每位成员的提交须分布在整个开发周期内，禁止最后一周集中提交（此项为 teamwork 评分直接观测点）。

6.3 最低协作指标

指标最低要求
每位成员的 commit 数≥ 8
每位成员的 PR 数≥ 2
代码审查记录每个 PR 至少 1 条他人评论
提交时间跨度覆盖开发周期的 ≥ 70%

7. 演示要求

时长按课程规定（假设 10–15 分钟），按以下叙事线分工，不按时间机械切分：

7.1 成员 A —— 定位与可复用性论证（约 3 分钟）

  • 解释「为什么做库而不是做应用」；
  • 展示抽象边界图（1 页幻灯片即可）；
  • 打开 Doxygen 生成的文档页面，证明文档由源码注释生成、与代码同步。

7.2 成员 B —— 现场功能演示（约 5 分钟，关键环节）

  1. 构建并运行 simcore_demo，说明输出含义；
  2. 现场新建一个文件，编写一个最小实体（3–5 行），修改 demo 的 main 引入该实体，重新编译并运行成功。
  3. 明确口述：「新增实体只修改了使用者文件，simcore 源码零改动。」
第 2 步为强制项。若现场编译失败，functional 与 innovative 两项均可能被判不完整。须提前演练至少 3 次，并准备离线编译环境（不依赖现场网络）。

7.3 成员 C —— 工程与协作（约 3 分钟）

  • 打开仓库 Insights / Network 页面，展示各成员分支合并轨迹；
  • 指出一个具体 PR，说明审查与合并过程；
  • 说明测试如何运行（ctest）。

10. 范围外事项（明确不做）

以下内容不在本项目范围内，提出者须说明其对评分标准的具体贡献，否则不予纳入：

  • 图形界面、可视化渲染、OpenGL / SDL 集成；
  • 网络通信、多线程调度、并行仿真；
  • 序列化 / 存档系统；
  • 插件系统、脚本绑定（Lua / Python）；
  • 超过 200 行的示例程序。
理由：本项目在评分标准下的得分点集中在可复用性、文档质量与协作痕迹，而非功能数量。范围蔓延会挤占 W6–W7 的文档与演练时间，边际收益为负。
